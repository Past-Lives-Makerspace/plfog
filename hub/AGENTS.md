## Conversation threads (the shared thread)

Every two sided conversation uses one look and one rule (`core/AGENTS.md`, Shared thread): `components/thread.html` draws the messages (the viewer's side on the right, a member sees their own as "You"), `components/thread_composer.html` is the box under it (body, photos through `components/thread_photos_field.html`, the busy submit guard, a note saying who hears it), and `components/thread_script.html`, once per page with `components/busy_submit.html`, binds the photo drop zones and, on `?messages=<key>`, opens and scrolls to `[data-thread-open="<key>"]` (a boosted redirect drops a `#fragment`). Styles are `static/css/thread.css`, loaded by `hub/base.html`. Threads so far:

- **Feedback requests** (#693): the Feedback page and the admin request page, the request's own message first (`FeedbackRequest.thread()`).
- **Orientation bookings**: the member's booking page `hub_orientation_booking` (`/orientation/bookings/<pk>/`, the booking's member only; someone who runs it is sent to the request page's Messages, anyone else gets a 404), a Messages fold under the live booking on the member's card (`partials/_orientation_type_state.html`, on the guild, equipment and Orientations pages), the Messages card on the request page (`orientation_respond.html`, `id="messages"`), and a Messages item in each Bookings tab row menu. A checkout hold has none of these, and its booking page and message POST are 404s. The note beside Send shows only when someone would be told. Everyone posts to `hub_orientation_message` (`/orientation/bookings/<pk>/messages/`, POST): the booking's member as the member, anyone `_require_can_manage_booking` admits as the guild, anyone else a 404. A refused message renders the poster's page again with what they typed; a sent one lands on `next` (or the poster's page) with `?messages=<pk>` and the toast "Sent." plus `told_sentence()`. Move to Another Time's modal carries an optional message (`OrientationMoveForm.message`), and a decline's note is posted too; both ride in their own email.
- **Equipment reservations** (#974): no detail page, so the thread opens in one Messages modal per page (`partials/reservation_messages_modal.html`, `modal_id="reservation-messages"`) on the Reservations page's Bookings tab, the equipment's Manage > Reservations tab and Manage Bookings. A Messages button (`partials/reservation_messages_launch.html`: a row menu item on the Bookings tab and Manage Bookings, a button on the manage page's Needs Approval and Upcoming Reservations rows) loads `hub_equipment_reservation_messages` (`/equipment/reservations/<pk>/messages/`, GET, the fragment `partials/reservation_messages.html`; it marks the thread read and tells nobody; a plain GET redirects to the viewer's page) into it. Everyone posts to `hub_equipment_reservation_message` (`.../messages/send/`, POST). Access is `reservation_bookings.reservation_thread_side`: the member who booked is the member side, anyone `can_manage_equipment` admits (admins included) the managers, anyone else and any block a 404. A Send, refused or not, lands on `next` (or the poster's page) with `?messages=res-<pk>`; `reservation_thread_to_open` reads that key, only for a thread the viewer may read, and the modal partial then loads and opens it by itself, which is also how the message notices land (`member_messages_url`, `staff_messages_url`). The lists show a New message pill (`data-thread-unread`) from `with_unread_messages_for(user)`; the equipment page's Your Reservations Here links each row to the Bookings tab with its thread open (`partials/_equipment_my_messages_link.html`).
- **Classes** (#975, in the classes app): one Messages card, `classes/_components/class_messages.html`, under Where Your Class Is on the composer, on the class Overview and on the review page (where it replaced Review History), for whoever `ClassOffering.message_side` places (instructors; the class's reviewers, CMS Administrators and admins), and on a review link for whoever may decide its gate, signed out included. Each side is several people (`ClassMessage.member_user_ids` is every instructor); "You" follows the shared thread's rule. Posts go to `classes:class_messages` (`/classes/teach/classes/<pk>/messages/`, whose GET is the stable link in every notice) or `classes:class_review_message` from a review link; a refused one lands back with the reason, a sent one on `next` with `?messages=class-<pk>`.

## Home

`views.home` (`hub_home`) renders `hub/home.html` from `hub/home.py::build_home_context`, and answers `Cache-Control: private, no-store` (`_private_no_store`). The Upcoming card is one queue (#937, `partials/_home_upcoming.html`, rows from `partials/_home_upcoming_row.html`, `static/css/home-featured.css`): the heading "Upcoming", then the first item of `_upcoming_items(member)` as the featured card and the rest as the list under it, no item twice. `_upcoming_items` merges the member's orientation bookings, the events they can see (community events, guild meetings, studio hours, each opening its event page on its next date) and the materialized class rows, soonest first, capped at `UPCOMING_CAP` (5). Each `UpcomingItem` carries what the card shows: `kind_key` (the pill's and the poster's color), `view_label` ("View Class", "View Studio Hours"; an orientation booking names the owner page it opens through `opens`, "View Guild" or "View Equipment"), `photo_url` and `photo_position` (a class's `ClassOffering.card_photo_url` with the catalog card's crop, read from the session behind its `local-class-<pk>` row; an event's photo as its page crops it; an orientation type's own photo), `flyer_url` (events only; the class flyer is editor gated) and a class's `instructors`. Five queries however many items: one per source, then the sessions with their class and category and every instructor between them, skipped with no class row. An item with no photo shows a date poster in its kind's color (month, day, weekday, the time and the title, CSS only). The queue is `plUpcomingQueue` (`static/js/pl-upcoming-queue.js`): every 6 seconds the rows slide up one (a 450ms FLIP), the next item cross fades into the card and the one that was featured drops to the bottom; previous, pause and next sit beside the card's kind pill (no dots, since the list itself shows the order) and a time bar runs along the picture's foot. It holds while hovered, while anything in it has focus (a keyboard user's, or a link a click left focused; not the focus a click leaves on its own arrows), paused (the lasting pause, under `pl-rotator-paused:<user pk>:home-upcoming`, swept by `pl-rotator.js` like every rotator's) or in a hidden tab, never moves by itself under `prefers-reduced-motion` and moves without animating there; one item has no controls and no list. Without JavaScript the server's order stands: the first featured, the rest listed in date order. With nothing upcoming the card is the heading and the empty line. A Poll block (#925, `home_poll`, `polls.models.PollCard.open_for`) is the last member block, just above Get the App (#936), only while a site-wide poll is open, with no heading or empty state otherwise. Hide folds it to one line ("Poll", the question, a Voted pill once answered, Show); an inline script after the block keeps the choice per poll in `localStorage` (`pl-home-poll-<pk>`, "1" folded, "0" open) and, with nothing stored, folds a poll the member has answered (`data-poll-answered`, from `PollCard.has_voted`, and set by the script once an in place vote swaps in the results). Its "See Past Polls →" is Home's only way to Past Polls since the quick link went in #936. Admin Tools' Tools section has the Polls card (`tool_polls`, admins). A guild page carries a Polls tab (`guild_polls`, `show_polls_tab`, `polls.models.GuildPolls`) when the guild has a poll or `can_edit_this_guild`, never on the guilds surface; `polls/AGENTS.md`.

Above everything on Home, for every viewer of Home with a membership or without one, crawls the Spotlight messages ticker (#889, a ticker since #935; `partials/_home_announcements.html`, `static/css/home-announcements.css`): `HomeBanner.load(now)` in `hub/home.py`, one query for `Announcement.objects.live(now)`, None while nothing is live, so Home is the only page that reads them. One slim line, a megaphone, the messages one after another right to left with a dot between them (`Announcement.inline_html`: bold, italic and links kept, paragraphs and breaks as spaces), and an X; a `<section aria-label="Spotlight messages">` whose second copy of the list is `aria-hidden` and `inert`, so a screen reader reads it once and the keyboard never lands in the copy. The crawl is a CSS animation paused on `:hover` and `:focus-within`; the pacing script (`partials/_ticker_pace_script.html`) sets its length from the list's width and `SiteConfiguration.spotlight_crawl_speed` (#942, 25px a second by default, read from the `feature_flags` context processor, so no query of its own) and stretches each list to the line, and under `prefers-reduced-motion` nothing moves and the messages wrap. Its X keeps `HomeBanner.signature` in localStorage (`pl-home-announcements-closed`) and removes the ticker; the same script removes it before first paint on every load until the live set changes (a new, edited, begun or ended message; a new order alone does not). Every storage call is in a try, so with storage blocked the ticker simply shows.

The speed is set on Admin Tools > Spotlight's Spotlight Messages card (`spotlight_views.hub_admin_spotlight_crawl_speed`, `/manage/spotlight/crawl-speed/`, admin only, `SpotlightCrawlSpeedForm`): a Crawl speed slider, 10 to 80 px a second in steps of 5, saved when it is let go over htmx with a toast; a refusal is a 400 with an error toast and the slider goes back to the stored speed. Under it a preview, the same track (`partials/_ticker_track.html`, inert) and the same pacing, crawls the live messages, or a sample line while none are live, at the slider's speed as it moves.

Home's header is the utility row (#1007, the layout Felix picked on 2026-10-29; `partials/_home_utility_row.html`, `static/css/door-code.css`): above the greeting, full content width, the labelled What's New button (`partials/_whats_new_button.html`, for a viewer `request.view_as.is_member` admits) and Show Me Around (`_home_tour_link.html`, 2.4rem tall like the button) on the left, and from 1200px the Door Code chip on the right; the greeting and its description then run the full width (`page_header.html` with no action slot, inside `.pl-home-greeting`, the description one line from 1200px), and the quick links come before the tour banner and the Get Started checklist at every width. The What's New button loads `hub_whats_new` into the `whats-new` modal `hub/base.html` includes once for every hub page (`components/modal.html`, `lg`; #1030 moved it out of the three pages that carried it) and opens it. Its dot and the once per 10 s pulse (`pl-whats-new-btn--unseen`) follow `core.whats_new.WhatsNew.unopened`: an entry in the viewer's audiences that no open of What's New has covered (`Member.whats_new_opened`), so one open quiets it until a release adds an entry, whatever the badges' seen list says. `hub_sidebar` hands the same flag to every hub page as `whats_new_unopened`, a `SimpleLazyObject`, so only a page that reads it pays the one roles query (`core.whats_new.WhatsNew.audiences`). Styles are `static/css/guidance.css`, loaded by `hub/base.html`. Part 3 adds the New! badge (`{% new_badge %}`, `core/AGENTS.md`, Guidance) to the quick links (`calendar.events`, `classes.catalog`, `guild.voting`, `admin.tools`) and to the sidebar: the plain links (Calendar, the tools entry, Feedback) carry the tag and the feature links pass `new_key=` to `_sidebar_feature_link.html` (catalog, voting, equipment, orientations, meetings). `static/js/guidance.js` (head, once per document) posts `hub_whats_new_seen` on a click inside anything holding a badge and removes that key's badges in place.

## Admin Tools and Guild Tools (#912, #921)

`views.hub_admin_tools` (`hub_admin_tools`, `/tools/`) is one page under two names, decided by `views._tools_page_title`, which the `hub_sidebar` context processor also reads (`tools_page_title`, and `can_use_admin_tools` as its not None) so the sidebar entry, the Home quick link and the page never disagree. Admin Tools for an admin (`view_as` aware); Guild Tools for anyone else `hub.guild_tools.runs_a_guild` admits (a guild officer, or a guild's lead or staff, through `is_effective_staff` and `manageable_guilds`, so an admin previewing as a guild officer, or as a member who leads a guild, sees it as that viewer would); then Admin Tools, unchanged, for an instructor or a Billing or Calendar Administrator; else None and a redirect home. An actual admin previewing below admin never gets the capability cards (Payments, Reports, Manage Events) from their own standing.

`ADMIN_TOOL_SECTIONS` lists each section's `tool_*` flags; `admin_tool_sections` renders a section while one of its cards shows. Since #935 Manage Mailing Lists sits in Manage and Instructor Inquiries (admins) in Tools, so a guild lead or officer whose one Manage card is Manage Mailing Lists gets a Manage section holding it alone. Guild Tools adds the `guild` section first (`tool_guild`): one guild's Guild Settings, Orientations, Reservations (`?tab=reservations`) and Events (`?tab=events`), under its name, for the guild `GuildToolsGuilds.for_request` picks: `?guild=<pk>` when it names a guild from `manageable_guilds`, else the first, so a crafted query never shows another guild's cards; a select picker shows with more than one. The guild section also carries Cubbies (#977, `data-tool-guild-cubbies`, with the guild's open and out of service counts from `_guild_cubby_counts`) only while `tool_guild_cubbies` is true, `can_manage_cubbies` on the selected guild (#1015: its lead and staff, and admins; a Guild Officer who does not run it keeps the other four cards), and Admin Tools' Manage section the admins' Cubbies card (`tool_cubbies`). In Guild Tools, Orientations moves to Reports as Orientation Bookings (`tool_orientation_bookings`, the Orientations page's Bookings tab), and Registrations (`tool_registrations`, `classes:admin_registrations`) joins while a guild they run has a class. Admin Tools never shows those three.

Right of the title (`.pl-tools-head`, `static/css/admin-tools.css`) sits the What's New button (#1007 part 3): `{% whats_new_button "admin" %}` on Admin Tools, `"guild"` on Guild Tools (the `guild_tools` flag decides), loading `hub_whats_new?feature=` into the `whats-new` modal the page includes. Cards with a registry key carry `{% new_badge %}` inside their title: the guild section's Guild Settings (`guild.staff`), Orientations, Reservations and Cubbies; Manage Events, Manage Members, the admins' Cubbies (`guild.cubbies`), Email Members, Reports (`admin.reconciliation`), Registrations (`admin.payment-report`) and Activity (`admin.site-activity`). The guild page (`guild_detail.html`) does the same: `{% whats_new_button "guild" %}` in `.pl-guild-statbar__actions` before the Join / Member CTA, and badges on the Orientations, Reservations, Cubbies, Wiki, Meetings and Polls tabs, which `{% tab_picker %}` mirrors into the phone picker.

## List / Calendar pages

The Orientations and Reservations pages (#502) open on List and build their calendar only for `?view=calendar`; otherwise the Calendar pane fetches the shell once on first open (`static/js/list_calendar.js`, any placeholder carrying `data-lazy-pane` and `data-pane-src`). Both reuse the guild page's shell (`partials/guild_calendar_app.html`) with `cal_key` and `cal.legend`; `hub/calendar_pages.py` builds their context on `hub/calendar_window.py` (`calendar_window_context`), the one place every calendar's date arithmetic lives, from rows in `hub/calendar_entries.py`.

The Orientations page's Bookings tab (#626, `?view=bookings`) loads the same way. Its rows are scoped by `membership.permissions.manageable_orientation_bookings` (the queryset form of `_require_can_manage_booking`) plus the viewer's own; a member who runs nothing sees only their own. The Reservations page's Bookings tab (#627) is its twin, scoped by `membership.permissions.manageable_reservations` (the queryset form of `can_manage_equipment`); its staff view adds a Needs Approval chip, with a count, while requests on equipment the viewer manages wait for approval (#748), and Approve and Decline Reservation in a waiting row's menu post to `hub_equipment_reservation_approve` and `hub_equipment_reservation_decline`, the same endpoints as the manage page's Needs Approval card. Both lists pass `honour_preview=True`, so an admin previewing as a member sees what that member would; action gates never pass it. Shared pieces live in `hub/bookings_tab.py` and `static/css/bookings-tab.css`.

## Cubbies tab

The guild page's Cubbies tab (#977, `partials/_guild_cubbies.html`, `static/css/cubbies.css`) shows while `Guild.show_cubbies_tab` is on, on the members surface, to a linked Member; `guild_detail` loads it through `membership.cubbies.CubbyTab.for_page`. Off, nobody sees the shelves, staff included (they build in the manager), but a member who rents a cubby there still gets the tab with only their Your Cubby cards, so they can always cancel or fix their card (#978). `?tab=cubbies` opens it. Grid draws each active unit holding an active cubby as a shelf (an empty square is a blank cell), List shows one row per cubby with its place in words (`Cubby.position_text`); phones open on List. No cubby yet: "No cubbies yet." and, for whoever `can_manage_cubbies` lets in (the guild's lead and staff, and admins, #1015), Set Up Cubbies.

Renting (#978, `cubby_rental_views.py`, forms in `cubby_rental_forms.py`): tapping an open cubby loads the Rent This Cubby sheet (`hub_cubby_rent_sheet`, `cubbies/_rent_sheet.html`) into the `cubby-detail` modal; its pay what you want chips and Other box share one Alpine state (`cubbies/_amount_state.html`) that words the floor rule the way the server does. Continue to Payment posts `hub_cubby_rent`: an amount refusal re-renders the sheet, a hold answers `HX-Redirect` to Stripe, and a cubby someone just took lands back on the tab with a toast. Stripe returns to `hub_cubby_checkout_return` or `hub_cubby_checkout_cancelled` (a signed token naming the rental and its cubby). Each live rental of the viewer's is a Your Cubby card (`partials/_guild_cubby_mine.html`) above the shelves: Change Amount loads `hub_cubby_rental_amount` into its own modal, Cancel Rental confirms first and posts `hub_cubby_rental_cancel`, Keep My Cubby posts `hub_cubby_rental_keep`, and Manage Payment is a GET to `hub_cubby_rental_portal` (links carry `hx-boost="false"`; the payment emails link it too). Every rental button reads its rental through `CubbyRental.objects.for_actor`, so anyone but the renter or an admin gets a 404. A rental guild staff assigned (#979) reads "Assigned by guild staff", has no Change Amount or Manage Payment, and its Cancel Rental ends it today. Home's Your Guilds card lists one "Your Cubby: A3, Glaze Wall →" line per live rental (`home._my_cubbies`).

Waitlist (#980, `cubby_waitlist_views.py`): while every cubby is taken the tab's Every Cubby Is Taken card offers Notify Me When One Opens, a POST to `hub_cubby_waitlist_join` (`/guilds/<pk>/cubbies/waitlist/join/`); a member on the list sees You're on the List with their place (`CubbyTab.waitlist_entry`, `waitlist_place`), full or not, and with the Cubbies tab switched off too (`partials/_guild_cubby_waiting.html`), and Leave the List confirms first and posts `hub_cubby_waitlist_leave`. Both land back on the tab with a toast. The staff Rentals tab's Waitlist chip (`?show=waitlist`, counted as "Waitlist (3)") swaps the table for `cubbies/_waitlist.html` (`cubbies.WaitlistRow`: place, name, joined date, Remove; one card per member below 768px; "No one is waiting." when empty). Remove confirms and posts `hub_cubby_waitlist_remove` (`/cubbies/waitlist/<pk>/remove/`), a 404 to anyone `can_manage_cubbies` refuses; the member is not told. Turning the Cubbies tab switch on (`hub_guild_cubbies_settings_save`) tells the line about each open cubby.

## Email Members (the sending feature)

Called Announcements until #920; code names (`AnnouncementDraft`, `hub_compose*`, `hub_announcements`, `_announcement_rows`) kept theirs. The Email Members card on Admin Tools and Guild Tools carries a "Formerly called Announcements" pill (one line in `hub/admin_tools.html`), and Manage Mailing Lists (`tool_mailing_lists`, in the Manage section since #935) opens the page's Mailing Lists tab (`?tab=mailing-lists`: `membership.permissions.manageable_guilds`, each row to that guild's Guild Settings `?tab=announcements#mailing-list`; a viewer with a list but no Drafts or Sent, such as an officer on no guild's staff, gets that tab alone). Guild Settings' tab reads Email Members; its key stays `announcements`. The composer (`hub_compose*`) and the Email Members page share one visibility rule, `_announcement_rows(request, member)` in `hub/views.py`: a row is visible and actionable exactly when `_compose_audience_forbidden(request, draft.audience_value)` is `None` (admins short-circuit to every row). Every composer lookup that takes a `draft_pk` goes through `_handled_draft`, which applies it to resumable rows only. Drafts are shared; `author` is whoever saved last, and the sender once sent. Send sends once (#1038): the Ready to Send modal sits inside the wizard form, which carries the `components/busy_submit.html` markers, so the first tap on Yes, send it disables it and Cancel (`data-pl-busy="hold"`, disabled without the label swap) until the page moves on; and a fresh compose posted again within a minute by the same sender with the same target, body and recipients (`AnnouncementDraft.recent_twin_of`; the channel switches are not part of the match) is treated as that send's repeat, saved nowhere, and refused onto the Sent tab, also while the first send is still running: `send_in_request` counts `send_attempts` up before the fan-out (never `send_requested_at`, which would hand the row to the queue job), `sending_in_request` reads it back for a minute after the row's last save, a `draft_pk` in that state is refused before `save_from_form` resets the count, and a plain saved draft is never a twin.

Guild leads (`leads`) and All Instructors (`instructor`, #806) are admin only audiences sent in the request through `emit("site_announcement")` with an explicit recipient set, so each person's makerspace announcement preferences apply unless the send is urgent. All Instructors is `Member.objects.instructors()`, signed in or not; an instructor with no account is emailed at the address on file only while Email is on, and the composer's count (`instructor_reach`) moves with the Email switch.

On a guild or class announcement the recipient checklist carries "Add people" (#729): a searchable list of members not yet listed with one "Add selected" (`static/js/compose_add_people.js`, the `composeAddPeople` component), and an "Add email addresses" box vetted by `hub_compose_add_addresses` (`classify_announcement_additions`). A guild send saves everyone added to the guild's `GuildMailingListEmail` list (`Guild.remember_announcement_recipients`, in `AnnouncementDraft.send`); a row with a `user` is a saved member, listed by name and reached as a member (`Guild.mailing_list_users`), removed in Guild Settings. A class send saves nothing, and a draft save never does.

## The Spotlight (#709)

The top left of every hub page for members: since #935 a static version card (`partials/_spotlight.html`), the version pill, which opens the changelog, "Updated X" from the newest changelog entry (`hub.spotlight.LatestUpdate`) and Details, joined to the logo above the sidebar's divider. No Spotlight messages (they crawl across the top of Home, above), no meeting and no minimized state. `hub_sidebar` sets `version_card` from `hub.spotlight.sees_spotlight` (members, not guests (#691), former members or signed out visitors; the polls app's `can_vote` reads the same rule) and `latest_update`, with no query; everyone else keeps the bare version number and the plain changelog modal. `static/js/spotlight.js` is an Alpine store with `expand()` and `showChange(anchor)`.

Details opens `components/modal.html` "spotlight-expanded" with `partials/_spotlight_expanded.html`: the latest update when the changelog has one (`partials/_spotlight_update.html`, which opens the changelog at it); Suggest a Feature / Report a Bug (`?category=`); and "Version X.Y · What Changed", which shows `includes/_changelog_pages.html` (five a page; the plain modal on public, login and admin pages uses it too). A `#changelog-<slug>` link opens the panel on that entry's page.

## Common Pattern

All views call `_get_hub_context(request)` for sidebar data (guild list, user initials) and `_get_member(request)` to get the logged-in `Member`. Views gracefully handle `member is None` (unlinked account).

## Forms (hub/forms.py)

- `VotePreferenceForm` — 3 guild FK selects (guild_1st, guild_2nd, guild_3rd)
- `ProfileSettingsForm` — edits Member fields (pronouns, about_me, discord_handle, etc.)
- `EmailPreferencesForm` — email notification toggles
- `BetaFeedbackForm` — bug/feature/general feedback; `form.submit(user=user)` saves a `core.models.FeedbackRequest`, then emails the Webmasters with a link to it
- `ThreadMessageForm` — one message on any shared thread (`core.threads`): a body and photos with the Feedback form's photo field and caps (`clean_feedback_photos`); `error_summary()` for a redirect
- `FeedbackCommentForm` — `ThreadMessageForm` labelled Comment, for a feedback request's thread
- `FeedbackRequestAdminForm` — the inbox's status, optional comment and GitHub link (a plain Form, so the instance keeps its saved values until `apply_admin_update`)
- `SiteSettingsForm`, `MemberAgreementSettingsForm`, `ManageFeaturesForm`, `ManageCmsForm`, `AutomationsForm` — one page's columns of `SiteConfiguration` each (#922); a field belongs to exactly one, because a checkbox a page does not render reads as off on its save. The four slices save with `update_fields`, so one page never puts back what another page just changed
- Self-service tab-entry form: `billing.forms.TabItemForm` with `context="member_tab_page"` (replaces the old `AddTabEntryForm` removed in v1.5.0)
