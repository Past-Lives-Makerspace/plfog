## The spine: help keys

One stable dotted key per documented capability, e.g. `voting.rank-guilds`, `teach.create-class`, `guild.manage-staff`. Contract all four specs honor:

- Format: `<area>.<action-slug>`, lowercase, dots + hyphens only.
- A key resolves to: a KB article section (article slug + anchor), a hover-help short_text (Info View), and optionally a tour step target (`data-help-key="<key>"` on the DOM element).
- The registry is **in-code** (a module-level dict, e.g. `core/help_registry.py` or `membership/help_registry.py` — Spec A picks the home and the others follow): `{key: {title, short_text, article_slug, anchor}}`. No DB model for topics (YAGNI; content is repo-authored). Tours reference keys; the Info View endpoint serves the registry as JSON.
- KB article sections carry `id` anchors derived from keys so hover panels and tour steps can deep-link "Read more".

## Verified voting facts (for article 6 & 24 — confirmed in code 2026-08-10)

- One persistent ranked ballot per member (`VotePreference`), editable **anytime** — the vote is rolling; there is always an open vote for the current month's cycle.
- The cycle is the calendar month; the UI shows it closing on the last day of the month (`membership/cycle.py get_cycle_context`). Standings are live; there is no hard lock.
- **Auto-snapshot:** `core/management/commands/take_cycle_snapshot.py` runs on the 15-minute cron; on the first tick of a new month it captures the just-closed cycle exactly once (EventDelivery dedupe + window guard), gated on `VotingSettings.auto_snapshot_enabled`, then **auto-sends results emails** (`snapshot.send_results()`). Admins can also snapshot manually (`/admin/take-snapshot/`, hub voting admin); the auto job skips if a snapshot already exists in the window.
