# Meetings — Spec & Implementation Plan

**Status:** Spec only — not yet approved to build.
**Date:** 2026-08-11
**Surface:** FOG hub `pastlives.test` — new `/meetings/` section (sidebar entry), the guild detail "Meetings" tab, and the retirement of the guild-edit "Meeting Notes" tab.
**Related:** Absorbs the member-built agenda app (github.com/stvncx/agenda-stevencox-app, deployed at agenda.stevencox.org). Replaces the `GuildMeetingNote` feature. Rides the CommunityEvent calendar/Discord rails — no new sync machinery.

---

## 1. Summary

Today a guild's meeting record is a Markdown "Meeting Notes" post written after the fact, and the agenda before the meeting lives nowhere — except in Steven's standalone agenda app, which only he can use. This spec makes **Meetings** a first-class FOG feature: one workspace page per meeting that starts life as the agenda and evolves into the minutes. A secretary creates an empty meeting and fills it in place — agenda topics in a focus-mode accordion, attendance with strikethrough absentees, action items with done-checkboxes and red priority flags — with autosave everywhere and no Save buttons. Any member can propose an agenda item for an upcoming meeting; leadership approves, declines, or edits-then-approves, and the proposer is credited on the item. After the meeting, leadership approves the minutes and the page locks into the permanent record. A cross-guild **Meetings** home in the sidebar gives everyone the upcoming list, the per-guild "Most recent ✓ / Next scheduled" coordinator table, and a browsable archive.

It serves both per-guild meetings and cross-guild guild-lead ("council") meetings, and it plugs into the existing CommunityEvent rails for Google Calendar, Discord, and reminder emails — creating a meeting can put it on the calendar in one step, and a new `video_call_url` field surfaces "Join meeting" buttons everywhere the meeting appears.

The original developer must recognize their app in ours. The binding recognizability checklist: (1) a single agenda-and-minutes page that evolves from plan to record; (2) focus-mode one-open accordion with dimming and click-dim-to-collapse, plus the open-action-count badge on collapsed items; (3) action items with done-checkbox + red priority flag nested under their topic; (4) approve → lock lifecycle with an archived artifact; (5) create-empty-then-fill + autosave-on-blur, no Save buttons on the workspace; (6) the coordinator dashboard with the per-guild "Most recent ✓ / Next scheduled" table and minutes index; (7) the Monthly / named-Special meeting convention; (8) attendance with strikethrough absentees.

### Locked decisions (from brainstorm Q&A)

| Decision | Choice |
|---|---|
| Placement | New sidebar entry **"Meetings"** — the canonical home (upcoming list, coordinator dashboard, browsable archive with guild/year filters). ## 4. Data model

All new models live in `membership/models.py`. Scope rule used throughout: **`guild` NULL means the cross-guild council meeting** — the same convention as `CommunityEvent.guild` (nullable → site-wide).

```python
class Status(models.TextChoices):
    DRAFT = "draft", "Draft"
    APPROVED = "approved", "Approved"
```

- `Meta.ordering = ["-scheduled_date", "-created_at"]` (newest first; undated drafts sort last via `F("scheduled_date").desc(nulls_last=True)` in the archive queryset).
- Indexes: `models.Index(fields=["guild", "-scheduled_date"], name="idx_%(class)s_guild_date")`; partial `models.Index(fields=["status"], name="idx_%(class)s_draft", condition=Q(status="draft"))` (the home page's "Needs attention" strip (§6.2) and the upcoming query filter on drafts constantly).
- Constraints: `CheckConstraint(condition=Q(is_special=True) | Q(special_title=""), name="ck_meeting_special_title_only_when_special")` — the `is_special` autosave cleaner keeps this satisfiable by clearing `special_title` in the same save when the toggle goes off (§5.2), so the constraint is the backstop, never the error path; `UniqueConstraint(fields=["legacy_note_id"], condition=Q(legacy_note_id__isnull=False), name="uq_meeting_legacy_note")` (idempotent migration).
- `__str__` → `self.display_title` + date, e.g. `"Woodshop — Monthly Meeting (2026-08-14)"`.
- Properties: `display_title` (`"{guild.name|'Council'} — {Monthly|special_title|'Special'} Meeting"` — the absorbed app's naming convention verbatim); `is_locked` (`status == APPROVED`); `scope_label` (`guild.name` or `"Council"`); `starts_at` (aware datetime from date+time, or `None`; mirrors `NextMeeting.has_time` handling).
- Manager/queryset (`MeetingQuerySet`): `upcoming()` (`scheduled_date >= today`, drafts and approved both — an approved agenda for a future meeting still shows; **ordered ascending** `(scheduled_date, scheduled_time nulls-last, pk)` so `.first()` is the *soonest* meeting, overriding `Meta.ordering`), `past()`, `archive()` (everything **not** upcoming: past meetings **plus undated drafts**, dated rows newest-first, undated last via `nulls_last` — an interrupted create-empty-then-fill draft is always reachable from the archive, §6.2 Zone 3), `needs_attention()` (undated drafts + past-dated drafts still unapproved — the two editor failure modes, feeding the home's editor strip §6.2), `for_scope(guild)` (guild or `guild__isnull=True`), `approved()`, `drafts()`, `visible_to(user)` (everything — all meetings are member-readable; exists as the single seam if that ever changes).

## 5. Business logic (fat models)

Views stay thin: parse request → permission guard → model method → partial/204+toast.

### 5.1 Permissions (`membership/permissions.py`)

- `can_edit_meeting(request, meeting) -> bool` — guild meeting: `can_edit_guild(request, meeting.guild)`. Council: FOG admin OR the user holds lead/staff authority in **any** guild (same membership test `all_guild_leads` resolves). View_as-aware like its siblings.
- `can_propose_to_meeting(request, meeting) -> bool` — guild meeting: any active member of that guild (plus its leadership/admins trivially). Council: guild leads/staff/admins only. Always `False` once `meeting.is_locked` or the meeting date is past.

### 5.2 The autosave contract (workspace only)

- **Endpoints:** one per object — `POST /meetings/<pk>/save/`, `/meetings/items/<pk>/save/`, `/meetings/actions/<pk>/save/`, `/meetings/attendees/<pk>/save/`. Body: `field` + `value` (form-encoded). Each view holds a per-model **whitelist dict** mapping field name → cleaner (`{"name": str.strip, "minutes": sanitize_rich_html, "scheduled_time": parse_half_hour, "present": _bool, …}`); an unlisted field is a 400 (fail loudly). The cleaner-validated value is saved with `save(update_fields=[…])`.
- **Client timing:** text inputs/textareas save on **blur, only when changed** (dirty check against the last-saved value — the absorbed app's exact behavior); checkboxes/selects/flags save on **change**; Quill fields save on **collapse/blur when dirty**. No keystroke-debounced saving — blur *is* the debounce; a 400 ms trailing debounce applies only to the rapid-fire controls (present toggles, flags) to coalesce double-clicks.
- **Feedback:** success → `204` with `HX-Trigger: {"meeting-saved": {}}`; the workspace's Alpine indicator flips "Saving… → Saved ✓". Validation failure → `422` + `trigger_toast(response, <message>, "error")` and the field re-renders its last-saved value.
- **Error contract (the workspace's `htmx:responseError` handler switches on status — the "connection" message is reserved for genuine network/5xx):**
  - **403 — lock race.** Someone approved the meeting while this editor had it open. Toast "These minutes were just approved and locked." then a full `location.reload()` — the page comes back in locked mode instead of silently eating every subsequent blur. (Losing the one in-flight value is the accepted cost; the reload is what stops the compounding loss.)
  - **404 — child row deleted by another editor** (item / action / attendee routes). Toast "That was just deleted by another editor." and the client removes the row's DOM node, leaving the rest of the workspace intact.
  - **404 — the meeting itself is gone** (any meeting-scoped route: `…/save/`, `…/approve/`, `…/items/add/`, etc.). The row-removal branch makes no sense for the page's own subject — instead: toast "This meeting was deleted." + redirect to `/meetings/`. The secretary never keeps typing into a ghost page. (The client distinguishes by which endpoint 404ed — meeting-pk routes vs child-pk routes.)
  - **Network failure / 5xx only** → indicator shows "Couldn't save — check your connection"; htmx retries on the next blur.
- **Coupled fields (server-side, same save):** setting `is_special=False` also clears `special_title` in the one `save(update_fields=["is_special", "special_title"])` — the §4.1 check constraint can never trip from the lone-field autosave; the client hides *and* clears the name input on toggle-off. Saving `scheduled_date` / `scheduled_time` / `is_special` / `special_title` / `video_call_url` additionally calls `sync_event()` (§5.3) when an **owned** calendar event is linked, so the calendar (including the location's video link) never drifts from the workspace.
- **Conflict behavior: last-write-wins**, accepted and stated. Two secretaries editing the same *field* within seconds is not a real scenario; different fields never conflict (`update_fields`). No version stamps, no merge UI (deferred with the rest of §10 if it ever bites).
- **Lock guard:** every autosave/mutation view calls `meeting.assert_editable()` first (below) — a locked meeting 403s server-side, matching the absorbed app's "Approved minutes are locked" 403 (and feeding the lock-race branch above).

### 5.3 `Meeting` methods

- `assert_editable() -> None` — raises `MeetingLockedError` (new domain exception in `membership/models.py`) when `status == APPROVED`. Called by every mutating path.
- `approve(*, by: User) -> None` — guard: `assert not is_locked` else `MeetingLockedError`; requires `scheduled_date` (approving an undated meeting raises `ValueError("Set the meeting date before approving.")`). Sets `status=APPROVED`, stamps `approved_by/approved_at` (re-approving after unlock **re-stamps** — locked decision). Side effects: `SiteActivity` `meeting_approved`; declines every still-`PENDING` proposal on this meeting with the note "The meeting was closed before this was reviewed." (each proposer notified — no proposal silently dies); `emit("meeting.minutes_approved" | "meeting.council_minutes_approved", target=self, context={"guild": self.guild}, url=workspace URL, period=f"meeting:{self.pk}:approved:{approved_at.timestamp()}")` — timestamped period so a re-approval after unlock announces the corrected minutes again.
- `unlock(*, by: User) -> None` — guard: caller must be FOG admin (the view enforces; the method asserts `is_locked` else `ValueError`). Sets `status=DRAFT` (approval stamps left in place as history until re-approve overwrites). `SiteActivity` `meeting_unlocked`. No broadcast — unlocking is corrective plumbing.
- `create_calendar_event(*, by: User) -> CommunityEvent` — guard: `assert_editable`; requires `scheduled_date` + `scheduled_time` (`ValueError` otherwise — a calendar event needs a start). Builds a `CommunityEvent(event_type=GUILD_MEETING|LEAD_MEETING, guild=self.guild, title=self.display_title, starts_at=self.starts_at, ends_at=+90min default, location=self.video_call_url or (self.guild.meeting_location if self.guild else "") or "", recurrence=NONE)` (council meetings have no guild — the expression must not touch `guild.meeting_location` unguarded) and calls **`schedule_or_go_live(actor=by)`** — announce + Google + Discord + reminders all ride the existing rails untouched. Links `self.event = event`, `event_occurrence = scheduled_date`, **`owns_event = True`**. Raises `ValueError` if already linked.
- `link_event(event, occurrence_date, *, by) -> None` — the "link an existing event" path; validates `occurrence_date` is one of `event.occurrences_in(...)` for recurring events. `owns_event` stays `False` — a pre-existing (possibly recurring, possibly shared) event is never mutated by the meeting.
- `sync_event() -> None` — called by the autosave view after date/time/title-affecting saves (§5.2). **Owned event only** (`event and owns_event`, else no-op): updates the event's `title` / `starts_at` / `ends_at` (duration preserved), `location` (recomputed with the same expression as `create_calendar_event` — a changed or cleared `video_call_url` reaches Google/Discord/reminders instead of a dead link living on), and `event_occurrence`, then re-pushes via the event's own `push_to_google` / `push_to_discord` (`membership/models.py:4622,4653` — the retry cron covers transient failures). Never re-`announce`s — a reschedule is a sync, not a new event. Clearing the meeting's date while owned-linked leaves the event where it was and lets the workspace show the mismatch line (§6.3) rather than guessing.
- `unlink_event(*, by: User) -> None` — guard: `assert_editable`, `event` set. Clears `event` / `event_occurrence` / `owns_event`. **Never deletes or edits the event** — for a merely-linked event that's obviously right, and for a formerly-owned one the calendar entry simply becomes a normal event; the UI copy tells the editor where to cancel it (§6.3). Non-destructive by design.
- **Deleting a meeting** (`Meeting.remove(*, by)` — the delete view calls this, not raw `.delete()`): guard `assert_editable` (drafts only — §6.3). When `owns_event`: first unwinds the calendar entry through the existing rails — `event.remove_from_google()` + `event.remove_from_discord()` — then deletes the event row, then the meeting (its confirm copy names this, §6.3 Footer). When linked-but-not-owned: the event is left completely alone (SET_NULL) and the confirm copy says so. No orphaned event ever keeps announcing a cancelled meeting.
- `add_item(*, by: User) -> MeetingAgendaItem` — `assert_editable`; creates an **empty** item (create-empty-then-fill). Returns it for the partial render.
- `add_attendee(*, member=None, guest_name="") -> MeetingAttendee` — `assert_editable`; XOR enforced by the constraint; duplicate member → `ValueError("Already on the list.")` surfaced as a 422 toast.
- `propose_item(*, by: User, title: str, why: str) -> MeetingItemProposal` — guard: `can_propose_to_meeting` (checked in view) + `assert_editable` + meeting not past. Creates the proposal; `emit("meeting.item_proposed", context={"guild": self.guild, "meeting": self}, url=workspace URL, period=f"meeting-proposal:{proposal.pk}:submitted")`.
- `carryover_actions()` — delegates to `MeetingActionItem.objects.carryover_for(self)` (§4.4); empty list for meetings with no `scheduled_date`.

### 5.4 `MeetingItemProposal` methods

Copying the CommunityEvent decision grain (`membership/models.py:4771+`), collapsed to the two-outcome shape the locked decision names:

- `approve(*, reviewer: User, title: str | None = None, why: str | None = None) -> MeetingAgendaItem` — guard: `state == PENDING` else `InvalidProposalTransition` (new domain exception); meeting must still be editable (`assert_editable`). Optional `title`/`why` overrides are the **edit-then-approve** path (the decision modal posts possibly-tweaked text). Creates `MeetingAgendaItem(meeting=…, name=title or self.title, description=why or self.why, proposed_by=self.proposed_by)` (lands at the agenda bottom via `sort_order` auto-assign), stamps `state/reviewed_by/reviewed_at/created_item`, and `emit("meeting.item_decided", context={"user": proposed_by}, …, period=f"meeting-proposal:{pk}:approved")` with copy "'{title}' was added to the agenda for {meeting.display_title}."
- `decline(*, reviewer: User, note: str = "") -> None` — same guard; note is **optional** (locked decision — unlike event declines). Stamps state + review fields; emits `meeting.item_decided` (period `…:declined`) with the note surfaced when present.
- `withdraw(*, by: User) -> None` — guard: `state == PENDING` else `InvalidProposalTransition`, and `by == proposed_by` — **proposer only** (the view enforces; anyone else, admins included, gets a 403 — a reviewer who wants a proposal out of the queue already has `decline` with an optional note, so an admin withdraw-on-behalf would be a second door to the same room with no UI). Sets `state = WITHDRAWN`. Silent — no emit, mirroring the event idiom's withdraw (the reviewer queue simply loses the row); the auto-decline in `Meeting.approve` skips withdrawn proposals.

### 5.5 `MeetingActionItem` methods

- `complete(*, by: User, in_meeting: Meeting | None = None) -> None` — `status=DONE`, `closed_at=now`, `closed_in=in_meeting` when closed from another meeting's carryover panel. Guard: only from OPEN.
- `dismiss(*, by: User, in_meeting: Meeting) -> None` — carryover-panel-only path; `status=DISMISSED` + stamps. Guard: only from OPEN.
- `reopen() -> None` — unchecking the box in its own meeting flips DONE→OPEN and clears the stamps (checkboxes must be un-checkable; dismissal is not reopenable from the UI — it's a wave-off).
- The lock guard for actions follows the **owning** meeting: editing an action inside a locked meeting 403s, but `complete`/`dismiss` **from a draft meeting's carryover panel remain allowed even when the source meeting is locked** — that's the entire point of carryover, and it's the one deliberate write into a locked meeting's data, stated here.

- **Drag-and-drop reordering** — deferred; v1 ships up/down buttons (call: one tiny endpoint buys the missing-in-the-original reorder UI without a sortable dependency or touch-DnD edge cases).
- **Search within minutes bodies** — deferred until the archive is big enough that guild/year filters stop being sufficient; the archive view is the seam.
- **Motions / aye-nay voting on agenda items** — out of scope; `VotePreference` et al. are funding-only and stay that way.
- **Autosave conflict handling beyond last-write-wins** — accepted risk (§5.2); revisit only on a real collision report.
- **Recurring meeting auto-creation from cadence** (a cron that opens next month's agenda automatically) — YAGNI for v1; "Start the agenda" from the cadence fallback is the manual version, and its usage will tell us if automation is wanted.
- **Meeting templates / standing agenda items** — not now; carryover covers the recurring-business need the original dev actually had.
