# #502 part 3: Calendar views on the Orientations and Reservations pages

Part 3 of 4 for #502 (does not close it; part 4 does). Both pages gain a List / Calendar tab pair. The Orientations calendar shows every upcoming bookable slot across every listed type, with seats left; the Reservations calendar shows what is taken across every active item. Both reuse the guild page's calendar shell. Mockups approved on the issue (2026-10-03): `mockups/502-orientations-reservations.html` on branch `fog/502-mockups`, views `orientations-calendar` and `reservations-calendar`; the approved default: month chips carry the type name only, owner and seats live in the list below and in Week view.

## Today

- The guild page's Guild Calendar tab renders `templates/hub/partials/guild_calendar_app.html` (Alpine shell: Week / Month toggle, legend filter buttons keyed by `cal.legend_guilds`, `focusEvent`, localStorage keys salted with `guild.pk`) wrapping `templates/hub/partials/calendar_content.html` (week grid, 4 week window, list below, `#pl-calendar-events-area` swapped by htmx from `events_url`). The context comes from `hub.views._get_calendar_context(request, week_offset, month_offset, event_page, guild)`, which reads `CalendarEvent` rows plus the synthetic entries of `hub/calendar_entries.py` (`guild_calendar_entries`: class sessions and orientation slots titled "Orientation"; `community_event_entries`), then does the window arithmetic, pagination, `month_event_pages`, `source_colors` and `legend_guilds`. The htmx partial is `guild_calendar_events_partial`.
- `CalendarEntry` (`hub/calendar_entries.py`) duck types a `CalendarEvent`: `pk, title, start_dt, end_dt, source, url, location, description, all_day, guild, feed, community_event, feed_key`; `source_key` routes classes by guild pk, everything else by `source`. Synthetic pks are offset (`ORIENTATION_PK_OFFSET`). `calendar_content.html` chips show `event.title|strip_date_suffix`; `calendar_event_item.html` shows title, time range for orientation and community sources, location, and links `event.url`.
- Part 2 built `/orientations/` (`hub/orientations_views.py`, cards with `id="orientation-type-<pk>"`) and part 1 the Reservations page (`hub_equipment_index`, `hub/equipment_views.py`); the item page takes `?day=YYYY-MM-DD` (`_parse_day`) for its schedule. `OrientationSlot.objects.bookable().with_seat_holding_count()` gives `is_full`; `holding_seats()` gives slots occupying equipment; `EquipmentReservation.objects.confirmed()`; `Equipment` has no color.
- `templates/hub/spaces.html` holds the tablist markup (`role="tablist"`, `.vote-tab`, `pane`).

## What changes

### 1. The calendar shell takes a legend, not only a guild

- `guild_calendar_app.html` gains two optional context names: `cal_key` (the salt for its localStorage keys and the `#pl-calendar-events-area` state; defaults to `guild.pk` so the guild page is byte for byte the same) and `cal.legend`, a list of `{key, label, color, logo_prefix}` dicts rendered as the filter buttons when present (otherwise `cal.legend_guilds` as today). No other change to the shell.
- `CalendarEntry` gains `legend_key: str = ""` (wins in `source_key`, before `feed_key`; documented beside it) and `chip_title: str = ""`; `calendar_content.html`'s two chip renderers use `event.chip_title|default:event.title` for the chip text and keep `title` for the `title=` attribute and the list.
- `hub/views.py`: the window, pagination and `month_event_pages` half of `_get_calendar_context` moves into `_calendar_window_context(all_events, week_offset, month_offset, event_page)` and `_get_calendar_context` calls it; a new `_entries_calendar_context(request, entries_for, *, week_offset, month_offset, event_page, legend, source_colors, events_url)` (in a new small module `hub/calendar_pages.py` with the two page builders below) calls `entries_for(fetch_from, fetch_to)` and the same window helper, so the two new calendars share every line of date arithmetic with the existing one and copy none.

### 2. The Orientations calendar

- `hub/calendar_entries.py` gains `orientation_page_entries(types, fetch_from, fetch_to) -> list[CalendarEntry]`: every `OrientationSlot.objects.bookable().filter(orientation_type__in=types, starts_at__date in range).with_seat_holding_count().select_related("orientation_type", "orientation_type__guild", "orientation_type__equipment", "orientation_type__equipment__guild")` that is not full: `pk=ORIENTATION_PK_OFFSET + slot.pk`, `chip_title=<type name>`, `title="<type name> · <owner name> · N seats left"` (seat / seats), `source="orientation"`, `legend_key=<guild pk>` (the owning guild, or the equipment's guild; `"makerspace"` for standalone equipment), `location=slot.location`, `url=<the type's card on the List view>` (`OrientationType.orientations_page_path` from part 2, which lands on the List pane and scrolls to the card). Full and cancelled slots are absent by construction.
- Page: `hub_orientations` gains the List / Calendar pair under the header (tablist markup from the Spaces page, Alpine `pane`, `?view=calendar` and a `#orientation-type-<pk>` hash both honored on load; the List pane keeps every card so anchors work). The Calendar pane includes the shell with `cal_key="orientations"`, `legend` = one chip per guild that owns a listed type (color `guild.calendar_color`, logo as the guild chips do) plus "Makerspace" for standalone equipment types (a fixed token color), `events_url=reverse("hub_orientations_calendar_events")`. The calendar context is built only when the page opens on the Calendar pane; otherwise the pane holds an `hx-get` to the partial that fires once when the member first switches (`htmx.ajax` from the pane switch), so the List view costs no calendar queries.
- Partial: `orientations/calendar/events/` named `hub_orientations_calendar_events`, `@login_required`, the same `week_offset / month_offset / page` parsing as `guild_calendar_events_partial`, renders `calendar_content.html`. The listed types are the same set part 2's page lists (reuse its builder; no second definition of "listed").

### 3. The Reservations calendar

- `hub/calendar_entries.py` gains `reservation_entries(items, fetch_from, fetch_to)`: every confirmed `EquipmentReservation` on `items` in range (`pk=RESERVATION_PK_OFFSET + pk`, a new offset constant beside the others; `title="<item> · <first name> <initial>."` from the reserver's `display_name`; `source="reservation"`; `legend_key=str(item.pk)`; `url=<item page>?day=YYYY-MM-DD`) and every `OrientationSlot.objects.holding_seats()` on the items' owned types in range (`title="<item> · Orientation"`, `source="orientation"`, same key and url). `calendar_event_item.html` treats `reservation` like `orientation` for the time range.
- Page: the same List / Calendar pair on `equipment_index.html`; `cal_key="reservations"`; `legend` = one chip per active item (`label=item.name`, `color` from a fixed palette of token colors indexed by the item's position in the name ordered list, stable for a given set); `events_url=reverse("hub_equipment_calendar_events")`; the same lazy load rule.
- Partial: `equipment/calendar/events/` named `hub_equipment_calendar_events`, `@login_required`, renders `calendar_content.html`. Items = `_equipment_queryset().active()` (the index's base set, unfiltered by chips; the legend filters client side).
- Open hours are not drawn (the item's page shows them); no new email or Discord post.

### 4. CSS

Nothing new beyond what the shell has; `.pl-tabs` for the pair exists. Both themes and phone width come from `calendar.css` as on the guild page; verify the legend row wraps at 390px with eight chips.
