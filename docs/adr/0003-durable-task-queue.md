# After save work runs on a durable task queue: django.tasks with django-tasks-db on our Postgres

**Context.** Work that follows a save (a Discord post, an email fan out, an external API call) cannot run inside the request, because gunicorn kills a request at 30 seconds. Since #845 it runs through `core.deferred.defer`: a thread in the gunicorn web process, started after the commit. Every merge to `main` redeploys that process, and a redeploy or an out of memory kill ends the thread mid run with nothing recorded. So each caller has had to build its own recovery: a database stamp saying the work is owed, and a job on the 15 minute cron that finds it and finishes it (`CommunityEvent.announcement_owed_since` and `finish_event_announcements` for event announcements). Every new feature that talks to Discord or sends email reinvents that pair, and #1148 and #1149 would have been two more.

**Decision.** New after save work is a Django task (`@task` from `django.tasks`, built into Django 6.0), enqueued with `core.tasks.enqueue_on_commit` once the transaction commits. In every environment but pytest the task backend is `django_tasks_db.DatabaseBackend` (the `django-tasks-db` package, 0.13), which stores each task as a row in our Postgres. A separate always on process, `python manage.py db_worker --no-reload` (no autoreloader, which `--reload` would start whenever `DEBUG` is on), runs as a Render Background Worker built from the same repo and Dockerfile, deploying from `main` with the web service's environment variables. It claims ready rows and runs them. Under pytest the backend is Django's `ImmediateBackend`, which runs a task at enqueue time. A task that finishes FAILED sends the Webmasters the same `automation.failed` alert as a failed scheduled job, at most once per task per Pacific day; results show in the admin under Background Tasks, where a superuser may delete them, and the daily `prune_task_results` job deletes them after 30 days (successes) or 90 (failures). The 15 minute `check_task_queue` job watches the queue (below). `defer` stays for its existing callers until each moves over.

**Why not the alternatives.** Keeping `defer` threads leaves the per feature backstop as the price of every new integration, and the backstop is the part that gets forgotten. Celery or RQ on Redis are the usual answer and bring retries, scheduling and monitoring, but also a second datastore to run, pay for, back up and watch, for a workload of a handful of tasks a day. `django.tasks` is Django's own interface, so a caller depends on nothing outside Django, and the backend can change later (to Redis, or a newer package) with no caller rewritten. The ORM backend keeps the queue in the Postgres we already run and back up.

**Consequences.**
- One more process, and one more paid Render instance. It holds one more Postgres connection and polls the table once a second when idle.
- A deploy no longer loses a task that has not started: it waits in the table until the worker is back. The web service works with no worker at all; tasks simply wait, and `check_task_queue` fails (which alerts the Webmasters once a day) when one has waited over an hour past when it was due.
- A task already running is not safe from every kill. On Render's stop signal the worker finishes the current task and then exits, but a task still running when Render's shutdown grace period ends, or a worker killed outright, is left marked running, and the worker never picks it up again. `check_task_queue` alerts on one running over an hour and marks one running over 6 hours FAILED, which alerts about that task and clears the check. Tasks should be short, and a long fan out split into one task per recipient batch: there is no worker heartbeat, so a task that really runs past 6 hours is marked FAILED and alerted on even though it then finishes.
- `django-tasks-db` 0.13 has no automatic retries: a failed task stays failed, and the alert is how anyone hears. Nothing runs a task again today; every task is still written to be safe to run twice, because a caller can enqueue the same work twice and retries can be added later without rewriting tasks. A failure the worker records without its signal (a task whose code no longer imports) is caught by `check_task_queue`, which alerts on every failure through the same once a day ledger.
- Enqueueing happens after the commit, so the task reads committed rows and a rollback enqueues nothing. The cost is a narrow window: a process that dies between the commit and the enqueue loses the task. An enqueue that raises after the commit is logged and alerts the Webmasters, and never fails the save. Enqueueing inside the transaction would close it for the database backend, but the immediate backend would then run the task before the commit under test.
- The worker deploys from `main` like the web service but runs no migrations, and tasks enqueued by the previous release run on the new code. A task keeps accepting the arguments its last release enqueued, and migrations keep to add before you remove.
- Arguments are stored as JSON, so callers pass ids, never model instances; `enqueue_on_commit` refuses anything else at the call and hands the task the JSON round trip, so the immediate backend under test sees what the database backend would.
