{% comment %}The Classes portal's one tab strip, rendered by the instructor shell and the admin shell alike (ruling 13). Ruling 14: every tab decides for itself whether it is offered, so an admin who also teaches gets all of them, and a plain admin gets no empty "My Classes" and no "Instructor Profile" — hidden, not blank. The order runs personal first, site-wide last, which is why an admin's Registrations now sits one slot earlier than it used to. Ruling 22: an admin who also teaches KEEPS "My Classes". Ruling 15: the labels are today's — "My Classes" for the instructor's own, "Classes" for the whole catalog — and the order is the only thing separating them. The two facts the rows read are about the VIEWER, not about a class, so they come off the request rather than from a context key every view would have to remember to set: `request.view_as.actual_is_admin` is the same preview-independent admin test the admin pages gate on, and `request.user.member.can_create_classes` is the teaching grant itself. A user with no linked Member resolves to nothing (Django renders a missing attribute as empty), so the teaching rows simply do not render for them. Catalog Activity sits inside the admin group even though Registrations, which a non-admin with catalog access can reach, renders above it: the feed spans the whole catalog.
