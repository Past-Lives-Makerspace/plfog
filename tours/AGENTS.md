# tours app

Facility tours: visits to the building for people curious about Past Lives, replacing the outside booking service used before (its code went in #950). Not the in-app guided tours (`core/tours.py`, `core.models.TourState`, `hub.forms.TourSettingsForm`, `?tour=`, `static/js/pl_tour.js`), which walk a member around the portal; nothing here touches or reuses those names. The round ships in five parts: #947 (this app's base: the Tour Guide permission, guide hours with seats, days off, Tour Settings, the booking model), #948 (public booking on tours.pastlives.space and the visitor emails), #949 (Upcoming and Past tabs with staff actions, below), #950 (the cairn front desk kiosk; the old booking service's code removed), #951 (Google Calendar per guide, below).

## Who

- **Tour Guide** is `AdminCapability.Capability.TOUR_GUIDE`, granted on a member's Permissions tab. Admins always have its abilities.
- Pages are gated by `hub.view_as.tour_guide_access_required` (Tour Guides and admins, by the actual role) and `fog_admin_required` (the Settings tab).
- **Where it lives (Felix):** not the sidebar. The Tours page is a card in the Tools section of the Tools page (`tool_tours` in `hub.views.ADMIN_TOOL_SECTIONS`), shown through `hub.view_as.has_tour_guide_access` (actual admin or Tour Guide, the billing cards' rule: an admin previewing below admin does not get it). A Tour Guide who is not an admin reaches the Tools page through `hub.views._tools_page_title`, which counts Tour Guide with the Billing and Calendar Administrator grants in its one query, so such a guide sees "Admin Tools" with the Tours card alone. The sidebar's Tools entry lights on every `/facility-tours/` path (`tools_nav_active` in `hub.context_processors`), and the page carries a "Back to Admin Tools" (or Guild Tools) link. Tour Settings is the page's admin only Settings tab, not a card of its own.
- Whose hours a request touches is decided once, in `tours.views._target_guide`: blank or the viewer's own pk is the viewer; anyone else is an admin's choice only (403 for a guide, before any form is read), and must give tours or already have hours (404 otherwise).
- An admin's guide picker lists everyone `guide_filter` admits (Tour Guides and admins, so an admin with no hours yet can be picked) plus anyone who already has hours.
- Whose hours visitors are offered is `tours.models.guide_filter`: an active member holding Tour Guide, an active `fog_role` admin, or a superuser. Revoking the permission stops the offer at once and keeps the rows.

## Availability

Never stored: `tours/availability.py` carves the hours on every read, so a change to the hours, a day off or a setting is in the next answer, with no nightly job.

- `open_tours(first_day, last_day, *, guide=None, include_full=False, now=None) -> list[OpenTour]`: every bookable tour over local days, minus days off, past the horizon (`today + booking_horizon_days`, included) and inside the minimum notice (`now + min_notice_hours`). Two guides with the same hours give two tours. Full tours drop out unless `include_full`. For visitors, a tour overlapping one of the guide's cached Google Calendar busy spans drops out too (#951); `staff=True` skips that filter. Five queries for any range (four for staff).
- `open_tour_at(guide, starts_at, *, lock=False, now=None) -> OpenTour | None`: one tour by guide and start, full or not, or None when it is not bookable now (including, for visitors, a busy time on the guide's Google Calendar, so a stale page's POST is refused too).
- `OpenTour`: `guide`, `hours_id`, `starts_at`, `ends_at` (both **UTC**), `seats`, `seats_taken`, `seats_left`, `is_full`, `key` (`<guide pk>-<UTC start YYYYMMDDTHHMMZ>`, the booking form's choice; `parse_tour_key` reads it back). `BookingWindow.at(now, settings)` is the horizon and notice as dates and an instant.
- **Every instant is compared and keyed in UTC (#948).** On the fall back night a carved 1:00 AM in the repeated hour is a local datetime whose offset depends on `fold`, and PEP 495 makes it never equal the same instant in UTC, so a booking read back from the database missed its tour. Templates show `OpenTour` times in local time through the `date`/`time` filters as always; specs reading a raw `.date()` or `.hour` must go through `timezone.localtime` first.
- Neither reads `accepting_bookings`: the booking page decides what a closed site shows, and staff keep moving tours while it is closed.

**Booking without overbooking (#948).** Inside `transaction.atomic()`: `tour = open_tour_at(guide, starts_at, lock=True)`; refuse when it is None or `tour.seats_left < party_size`; create the `TourBooking`; commit. `lock=True` takes `SELECT ... FOR UPDATE` on the guide's `TourHours` rows for that weekday (raising `RuntimeError` outside a transaction), so every booking of one tour queues on the same row lock, and on PostgreSQL's read committed each statement after the lock sees the bookings committed before it. A reschedule takes the lock of the tour it moves to.

## Public booking (#948)

**Host.** `TOURS_HOSTS` (default `tours.pastlives.space`, auto-added to `ALLOWED_HOSTS` and, as https, `CSRF_TRUSTED_ORIGINS`) is the `tours` surface in `core.middleware.SurfaceMiddleware`: the root's `path_info` is rewritten to `tours_public:book`, and only `TOURS_ALLOWED_VIEW_NAMES` plus allauth's `account_*` sign in views resolve there (everything else 404s). The views also 404 on every other host (`tours_surface_only`). `TOURS_BASE_URL` builds the email links. Chrome is `templates/tours/public/base.html` (the guilds surface's topbar, links off the host absolute; `parent_template` points allauth here on this surface), styles `static/css/tours-public.css`.

| View | URL name | Path |
|------|----------|------|
| `public_views.book` | `tours_public:book` | `/` on the host (`/tour/`): the date strip (`?date=`) and the day's times; `?tour=<key>` opens the form; POST books. Closed message while Tour Settings is not accepting. |
| `public_views.manage` | `tours_public:manage` | `/tour/b/<token>/`: the booking, its Reschedule and Cancel buttons while they apply; `?booked=1`, `?moved=1`, `?cancelled=1` land here |
| `public_views.reschedule` | `tours_public:reschedule` | `/tour/b/<token>/reschedule/`: the same date strip (tours with room for the party, not its own), a confirm, POST moves |
| `public_views.cancel` | `tours_public:cancel` | `/tour/b/<token>/cancel/`: GET confirms only (prefetch changes nothing), POST cancels |

**Links.** The emails carry `self_serve_token` itself: a random 43 character string stored on the row, so a link lives as long as the booking, a tampered or unknown token finds no row (a friendly 404 page, never a 500), and no signing key rotation breaks old links. Not the orientations' signed `make_action_token`: that one names one action and expires, and every tour page needs a row lookup anyway. Reschedule and Cancel refuse on GET and POST alike through `self_serve_refusal` (`refused.html`: too close with the support email, cancelled, past). While Tour Settings is not accepting bookings, Reschedule shows the closed message and moves nothing; Cancel keeps working.

**Abuse and privacy.** The booking POST spends one `record_keyed_attempt("tour_booking", client_rate_key(request))` (10 an hour, 30 a day, the guest RSVP's caps) before anything else, then a `website` honeypot (a filled one is sent back to the page and books nothing). Every form disables its button on submit (`components/busy_submit.html`, included by the tours base). `includes/google_analytics.html`'s `plCleanUrl` sends `/tour/b/<token>/...` as `/tour/b/redacted/...`, so a token never reaches Google.

**Service (`tours/booking.py`).** `book_tour`, `reschedule_tour`, `cancel_tour_by_visitor`, each inside `transaction.atomic()` with `open_tour_at(..., lock=True)` on the tour it lands on (the move and cancel lock the booking row first). Errors are `TourFullError` ("That time just filled up, pick another.", or "Only N seats are left at that time." when some remain, `seats_message`), `TourUnavailableError`, `TourLockedError(reason)`. A booking links to the signed in user, else to the account the email already has (left as it is); with neither and the toggle on (it starts on, Felix), `core.services.guest_account.ensure_guest_account` makes a GUEST account after the booking stands (invite only mode too, like the Eventbrite finish page). Nothing is made for an email that is a member's with no account (`Member.objects.unlinked_with_email`): some are userless on purpose (Member 529, Member 733). The same email, name (ignoring case and spacing), party size, guide and start booked again within `REPEAT_WINDOW` (10 minutes before `now`) raises `TourAlreadyBookedError` and sends nothing (a double press of Book); the page then says to check the email and shows nothing of the booking, never its token, since anyone may know a visitor's email. A different name or party is a booking of its own. `tests/tours/booking_spec.py` races four visitors for two seats on PostgreSQL (`postgres_only`).

**After commit.** `_after_commit` registers two `robust` callbacks, so they run only once the transaction commits and a failing email never keeps the calendar from hearing: `tours.notify.announce`, and `tours.signals.tour_booking_changed(booking, change, [previous_guide, previous_starts_at])` with `change` `booked`, `moved` or `cancelled`. The Google Calendar sync (#951) is connected to that signal in `ToursConfig.ready`.

**Emails (`tours/notify.py`, `templates/tours/emails/`).** `tour.visitor_update` (by `email_to`, no channel, off the settings matrix): confirmed, moved, cancelled, reminder, each with `build_ics` (UID `ics_uid`, SEQUENCE `sequence`, instants in UTC, `METHOD:CANCEL` for a cancel) and the Reschedule and Cancel links; the visitor shell `_base.html` has no members footer. `tour.booked` to the guide (email, bell, push on by default) and `tour.visitor_changed` (email, bell) on every visitor move or cancel; a move to another guide's tour tells the old guide it left and the new guide it was booked. Their audience is `Recipients.TOUR_GUIDES` (`core.events.resolvers.tour_guides`): the tour's guide, or the admins when it has none (#949: only an admin can see or act on a tour with no guide, so every Tour Guide holder no longer hears); the settings matrix files the rows under Tour Guide (or Admin). The reminder is `notify.tour_reminder_occurrences`, walked every tick by the `send_tour_reminders` job (period `tour:<pk>:reminder:<UTC start>`, so once per start, never for a cancelled tour). All six emails are in the email gallery.

**Known limit.** A booking is matched to its tour by `(guide, starts_at)` alone; it stores no link to the `TourHours` row. If a guide later changes a row's tour length or start, an existing booking whose start no longer falls on the new grid counts against no offered tour (its seats free up on paper) and appears on no carved tour. The Upcoming and Past tabs (#949) list `TourBooking` rows themselves, never the carve, so such a booking still shows there and can be moved or cancelled; nothing flags it yet.

## Staff actions (#949)

The Tours page's **Upcoming** and **Past** tabs (`tours/bookings.html`, one card per booking from `partials/_booking_row.html`): a guide sees their own bookings, an admin every guide's with a guide filter (`?guide=`; a guide naming anyone else gets a 403). Both are paged (25). Upcoming rows carry **Reschedule** (the `tour-reschedule` modal, its body `partials/_reschedule.html` loaded over htmx) and **Cancel Tour** (`confirm_modal` with an optional message, `confirm_note_name="message"`); Past rows carry **Attended** and **No Show**, posted over htmx so the row swaps in place with a toast. Reschedule and cancel answer `HX-Redirect` back to the tab they came from (`HX-Current-URL`, same site and under `/facility-tours/` only) with a flash, which the page shows as a toast.

- **Who may act.** `views._staff_booking`: a guide only on a booking whose guide they are, an admin on any (403 otherwise, crafted POST or not). `views._destination_guide`: a guide moves only within their own open tours; an admin may pick any guide who gives tours, which reassigns the booking. A posted tour key's guide goes through the same check.
- **Services (`tours/booking.py`).** `reschedule_tour_by_staff` and `cancel_tour_by_staff` take the visitor paths' locks (the booking row, then `open_tour_at(..., lock=True, staff=True)` on the destination), with neither the cancel cutoff nor the minimum notice (`BookingWindow.at(..., staff=True)`: any tour that has not started, still inside the horizon) nor `accepting_bookings`. A cancelled or started booking raises `TourLockedError` (`STAFF_LOCKED_MESSAGES`). `mark_tour_outcome` sets attended or no show on a tour that has started; attended stamps `UserProfile.completed_tour_at` (the tour's start) for a linked user only when it is empty, in one conditional UPDATE; correcting attended to no show clears the stamp only when it equals this tour's start, so an earlier tour's stamp stays.
- **Who hears.** The visitor gets the moved or cancelled email with the .ics (SEQUENCE raised) and the staff member's note (`emails/_staff_message.*`, `notify.note_label`: "A note from <first name>", or "from Past Lives" for an account with no name). Every tours `.txt` body is wrapped in `{% autoescape off %}` (plain text must not carry `&#x27;`); the HTML stays escaped. `notify.announce(..., actor=, staff_message=)` tells each guide involved except the actor: the guide on a move or cancel (`tour.visitor_changed`, copy naming who acted), and on a reassignment the old guide (it left) and the new guide ("Tour moved to you", `tour.booked`). A tour with no guide tells nobody. Every guide email and bell links to the Upcoming tab.
- **Seam.** `tours.signals.tour_booking_changed` fires after commit as for the visitor paths, with `actor` and `staff_message` added; a reassignment is a `moved` whose `previous_guide` differs from `booking.guide` (part 5 moves the Google event).

## Front desk kiosk (#950)

cairn, the lobby screen (`ssh cairn`), shows `/kiosk/` on the tours host: **I Booked a Tour** and **Schedule a Tour** (`tours/kiosk_views.py`, `tours/kiosk_urls.py`, namespace `tours_kiosk`, in `TOURS_ALLOWED_VIEW_NAMES`; templates `templates/tours/kiosk/`, styles `static/css/tours-kiosk.css`, reset `static/js/tours-kiosk.js`).

- **Key and cookie (`tours/kiosk.py`).** An admin makes or rotates the key on the Settings tab (`tours:kiosk_key`, Create Kiosk Link, then Rotate Key behind a confirm), which shows the link `TOURS_BASE_URL/kiosk/?key=<key>`. Opening it sets `pl_tour_kiosk`, a cookie signed with the site's secret (salt `tours.kiosk`, path `/kiosk/`, httponly, 400 days, renewed on every home visit) carrying the key's SHA-256, never the key, and redirects to `/kiosk/` without it. A cookie whose digest is not the current key's is refused, so rotating locks out every old screen. Without a valid cookie every kiosk path redirects to `/`, the public booking page: today's names never reach the open internet.
- **Check in.** All three ways at once (Felix): the email booked with (ignoring case), a name tapped in today's list (first name, last initial, time), or a name typed (`kiosk.name_matches`: case, spacing, accents (NFKD, combining marks dropped), word order, hyphens, apostrophes, dots and commas ignored; the whole name, the first name or names alone, the last name or names alone, or the first name and the start of the last, either way round). A tapped name and a pick list choice (POST `pick`) ask "Is this you? Sam R., 4:00 PM" first (`kiosk/confirm.html`): Yes, Check Me In posts `booking`, Not Me goes back, so a wrong tap never checks in someone else. Email, and a typed name with one match, check in at once. Only tours still booked for today match, never a cancelled or another day's. One match: `booking.check_in_tour` stamps `checked_in_at` and, after commit, `notify.tell_guide_checked_in` sends `tour.checked_in` (bell and push, "Your 4:00 tour is here", period per booking) to the guide, or to the admins when it has none ("A 4:00 tour is here (no guide)"); a second check in changes nothing and pings nobody. Check in never marks attended and never stamps `completed_tour_at`; the guide's Attended does (#949). Several matches: a pick list ("under that name", or "for that email"). None: "We Could Not Find a Tour Today" with Try Again and Schedule a Tour. Each check in POST spends one `record_keyed_attempt("tour_kiosk_check_in", client_rate_key(request))` (60 an hour, 300 a day), so a leaked key still cannot probe names at speed. The Upcoming tab's row says "Checked in at 3:52 PM".
- **Schedule a tour.** The website's flow (`public_views.post_booking(..., kiosk=True)`, `_picker.html`, `_book_form.html`) under the same notice and horizon, with `source="kiosk"`, on its own rate limit `tour_kiosk_booking` (60 an hour, 300 a day; `public_views.KIOSK_BOOKING_*`), never the website's `tour_booking`, since cairn shares the makerspace's public address with every phone on the Wi-Fi; never linked to whoever is signed in on the screen, the account toggle on as on the website. The confirmation never shows the visitor's links.
- **Nothing lingers.** Every kiosk view is `never_cache` (`no-store`), every form `autocomplete="off"`, and each POST redirects to a result page that pops its outcome from the session (`check-in/done/`, `book/done/`), so a reload or the back button shows nothing and goes home. `tours-kiosk.js` returns home after 60 seconds without input (`data-kiosk-idle`) and 8 seconds after a welcome or a booking (`data-kiosk-done`), with `location.replace`, and on a page restored from the back/forward cache.

|------|----------|------|
| `kiosk_views.home` | `tours_kiosk:home` | `/kiosk/` (`?key=` sets the cookie) |
| `kiosk_views.check_in` | `tours_kiosk:check_in` | `/kiosk/check-in/` (POST `pick` to confirm, `booking`, `email` or `name`) |
| `kiosk_views.check_in_result` | `tours_kiosk:check_in_result` | `/kiosk/check-in/done/` |

## Google Calendar per guide (#951)

A Tour Guide connects their own Google Calendar on the My Hours tab: each tour booked in their hours is written to it, and the times it shows them busy are not offered to visitors. Off (the card says so) until `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` are set, and always off on staging (`tours.google.is_configured`).

- **Sign in (`tours/google.py`, `views.tour_google_*`).** Per user web OAuth: authorization code, `access_type=offline`, `prompt=consent` (a refresh token every time, including a reconnect), `state` kept in the session under `tours_google_oauth_state` and popped on the callback (works once, compared in constant time), redirect URI `MEMBER_BASE_URL` + `/facility-tours/google/callback/`. Scopes, checked against Calendar v3's discovery document: `calendar.events.owned` (write and list events on calendars the guide owns) and `calendar.calendarlist.readonly` (the picker, and the account's email as the main calendar's id). Not `freeBusy`: it merges our own tour events with someone else's meeting over them, so it could neither leave our events out nor see a clash with a booked tour. A grant missing either scope is refused ("leave every box ticked"). Plain `httpx`, mocked with `respx`; the discovery client's `httplib2` is not.
- **Card (`partials/_google_calendar.html`).** Not connected: Connect Google Calendar (`hx-boost="false"`, it leaves the site). Connected: the account, Disconnect (`confirm_modal`), when busy times were last read, and the calendar picker (`forms.TourCalendarChoiceForm`, owned calendars, main one first as `primary`) with Save last. Broken: why, Reconnect and Disconnect. An admin on someone else's hours reads their state only (Google signs in whoever presses Connect), and the guide picker names each guide's state ("Calendar connected", "Calendar needs reconnecting", "No calendar").
- **Writes (`tours/calendar_sync.py`).** `queue_booking_sync` (the signal receiver) only marks the booking's `TourCalendarSync` row due, when its guide is connected or an event of it is already on a calendar; connecting and picking another calendar queue the guide's upcoming tours. The `sync_tour_calendars` job (every tick, `core/scheduled_jobs.py`) runs `sync_due_bookings`: each row is brought to what the booking says now (`sync_booking`): an event on the guide's chosen calendar titled "Past Lives tour: <visitor> (<party size>)" with the visitor's name, party, email and phone and the Tours page link in the description, marked `extendedProperties.private.plfogTour`; none for a cancelled tour; and an event on another guide's calendar (a reassignment) or another calendar is deleted first. Event ids are ours (`event_id_for`: `pltour<pk>s<8 base32hex of MEMBER_BASE_URL>`), so a create whose answer was lost, a reconnect, or a tour moving back updates the event in place (insert, 409, then PUT with `status: confirmed`). A failure leaves the row due with `next_attempt_at` 15 minutes, doubling to 6 hours; a row whose tour ended a day ago is given up. A row needing a broken connection waits, uncounted, until a reconnect.
- **Reads.** `read_busy` lists every event on the guide's main calendar and chosen one from now to the end of the horizon and keeps what blocks time: not cancelled, not shown as free (`transparent`), not a working location or birthday, not declined by the guide, and not ours. All day events count from local midnight. Merged spans are cached on the connection. The job reads anything older than 10 minutes and refreshes the picker's calendar list; `refresh_stale_busy`, called by `public_views.all_open_tours` (the booking page, reschedule and the kiosk), reads any connected guide with hours whose cache is older than 15 minutes, at most 4 seconds in all and 3 per call, and leaves one whose read failed alone for 5 minutes. A Google failure keeps the cache (or none); a sync bug is logged and the page still renders.
- **Clash with a booked tour.** Never taken away. `alert_busy_conflicts` (every tick) bells the guide `tour.calendar_busy`, "Your calendar now shows you busy during a booked tour", once per booking and start (period `tour:<pk>:calendar_busy:<UTC start>`).
- **Broken.** A refused token (`invalid_grant`, a 401, a 403 permission reason) calls `mark_broken`: one conditional UPDATE to broken clearing both tokens, so the guide gets `tour.calendar_broken` (email `emails/guide_calendar_broken.*` and bell) once per breakage. Broken busy times are ignored, so their hours offer as if unconnected. A key change that leaves the tokens unreadable also lands here (`EncryptedCharField` reads them as blank).
- **Disconnect** revokes the refresh token at Google (3 second timeout; the page says so when Google does not confirm), deletes the connection and forgets where its events were. Tour events already written stay on the guide's calendar; a reconnect updates them in place through the stable ids.
- **The job fails** (the Automations page shows it, the Webmasters hear once a day) when a write has failed 4 times in a row or a connected calendar has not been read for over an hour.
- **Staff override.** The Reschedule modal (`staff=True`) offers busy times anyway; the guide then gets the clash bell.

## Post-merge ops

- **Google Calendar for guides (#951).** In Google Cloud (the Past Lives project): enable the Google Calendar API; OAuth consent screen with the scopes `.../auth/calendar.events.owned` and `.../auth/calendar.calendarlist.readonly`; an OAuth client of type Web application with the authorized redirect URI `https://members.pastlives.space/facility-tours/google/callback/`. Both scopes are sensitive: **Internal** (only accounts in the Past Lives Google Workspace, no verification) works if every guide signs in with a pastlives.space account; **External** in Testing mode works for up to 100 listed test users but their refresh tokens expire after 7 days (every guide breaks weekly), so External needs Publishing and Google's verification. Set `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` on the Render web service and the scheduled tasks cron (the job refreshes tokens); `STRIPE_FIELD_ENCRYPTION_KEY` is already on both.

- DNS: a CNAME for `tours` to the Render service, **proxied through Cloudflare (orange cloud)**: the booking rate limit keys on `CF-Connecting-IP` (`core.abuse_limits.client_rate_key`), which only Cloudflare sets truthfully. Then add tours.pastlives.space as a custom domain on Render.
- The kiosk (#950), once the host answers: an admin presses Create Kiosk Link on the Settings tab; on cairn (`ssh cairn`) put that link in `/etc/kiosk.conf` in place of the slideshow URL and `systemctl restart kiosk`. Rotating the key later means doing this again.
- Owed: `core.UserProfile.tour_status_checked_at` was the old booking service's poll stamp and nothing writes or reads it since #950. It stays one release so the release still serving during the deploy keeps working (STANDARDS 10); a later release drops it with a `RemoveField`. `completed_tour_at` stays.
- The lobby slideshow's Book a Tour slide: a new Site Settings row defaults to `TOURS_BASE_URL` (`core.models.default_signage_tour_url`), but the production row keeps the value it holds; an admin changes Tour booking link in Site Settings to https://tours.pastlives.space once the host is live.
