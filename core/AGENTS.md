## Shared thread (`core/threads.py`)

One conversation model for every domain (feedback requests, orientation bookings, equipment reservations; classes next). Each domain keeps its own concrete tables on the abstract bases, never a generic foreign key: `ThreadMessage` (author User FK nullable SET_NULL with `related_name="+"`, body, created_at; a concrete model adds the FK to its object and may redeclare `author` to keep an older reverse name, as `FeedbackComment` does) and `ThreadPhoto` (image, created_at; the concrete FK is `related_name="photos"`). Which side wrote a message is derived: anyone but the member side's accounts is staff side, and so is a message with no author (a carried over note, signed with `staff_signature`). The member side is a set of accounts (`member_user_ids`): one for a feedback sender or a booking's member, several for a class's equal instructors; `components/thread.html` calls a member side message "You" only when the viewer wrote it, and names any other member side author. A concrete model fills in `member_user_ids`, `member_side_name`, `staff_signature` (default "Past Lives"), `_tell_member_side`, `_tell_staff_side`, `told_sentence` (the toast's second sentence) and optionally `after_write`. The rule: `post()` saves the message and its photos and tells the other side in one transaction, every time; `write()` saves and tells nobody, for a message that rides on another action's own notice (a decline note in the decline email). `ThreadOpening` is a member side first item that lives on the object itself (a feedback request's message and photos); it is drawn first and never posted. Templates and CSS: `hub/AGENTS.md`, Conversation threads.

## Registration Modes

`SiteConfiguration.RegistrationMode.OPEN` — anyone can sign up.
`SiteConfiguration.RegistrationMode.INVITE_ONLY` — only invited emails can register.

The allauth adapter (`plfog/adapters.py`) checks this before allowing new signups.

## Invite Flow

1. Admin calls `Invite.create_and_send(email, invited_by)` — creates `Member` placeholder with status=INVITED and sends email
2. Invitee clicks link → `allauth` signup pre-fills email
3. Adapter calls `invite.mark_accepted()` on successful signup

## Member Lockout (#409)

`core/member_lockout.py` holds the one rule: `lockout_reason(user)` returns `former` or `guest` (always, staff included; a guest is an account made from a class booking, #654) or `suspended` (while `SiteConfiguration.suspended_members_locked_out` is on), else None. It reads `Member.status`, never `User.is_active`, and knows nothing about surfaces; the three gates decide that:

- `AdminRedirectAccountAdapter.pre_login` refuses sign-in on the members surface only, so a former member can still sign in on book for their class receipts. A guest is the exception (#691): while `kiln_tickets_open` is on, it signs in on members to file kiln tickets.
- `biometric_unlock` always refuses (the app is the members site) and revokes the credentials.
- `MemberLockoutMiddleware` never logs out, because the session cookie is shared with book. On the members surface it redirects everything to the lockout page except that page, logout, `/static/` and `/health/`. On book it serves only `settings.LOCKED_OUT_BOOK_PATH_PREFIXES` (`/classes/`, `/account/`, `/accounts/`, `/static/`, `/media/`, `/health/`), because `MEMBER_ONLY_PATH_PREFIXES` is a blocklist that would otherwise open hub pages, `/api/` and the KB sign-in (`/o/`). Guilds and signage are untouched. The one exception (#691): while `kiln_tickets_open` is on, a guest on the members surface is served `/kiln/`, and every other members page sends it to `/kiln/` instead of the lockout page. A guest is also served `/hq/` (the Holiday Bizarre HQ) and, by resolved URL name (`GUEST_EVENT_URL_NAMES`), one event's public page, its flyer, its `.ics` and the guest RSVP post (#887), which the HQ links to; the page renders for a guest as for a signed-out visitor.

All send the member to `/accounts/locked/?reason=`, which renders on either host and shows the admin-editable message (`former_member_signin_message` / `guest_member_signin_message` / `suspended_member_signin_message`, General tab of Site Settings) and the support email. A signed-in viewer also gets a link to their bookings on book (`BOOK_BASE_URL`) and a log out link; an anonymous one gets "Back to login".

## Deferred work (`core/deferred.py`, #845)

`defer(task, name=...)` runs slow work after the current transaction commits, on a non-daemon background thread named `deferred:<name>`, so a request never holds its response for it. It is a thread, not a response close hook, because in a gunicorn sync worker the close hook still runs on the worker's main loop and WORKER TIMEOUT kills it at 30 seconds as before. The thread closes its own database connections when it ends and logs a failure instead of raising. A thread does not survive a redeploy or a kill, so every caller needs a database stamp and a cron backstop that finishes the work, and the work must be safe to run twice (the event announcement: `CommunityEvent.announcement_owed_since` and `finish_event_announcements`). Under test the root `conftest.py` swaps `deferred._schedule` for `run_inline`; a spec that needs the real thread sets it back to `after_commit_thread` and joins the `deferred:` threads, and `tests/core/events/conftest.py`'s `held_deferred` holds the work so a spec can check what the request left behind first.

## Cron health reporting (`core/healthchecks.py`)

`report_to_healthchecks()` wraps the body of each Render cron command (`run_scheduled_tasks`, `airtable_pull`) and pings its Healthchecks check: `/start` on entry, then success, or `/fail` when the body raised or the command called `run.fail(...)` for an error it caught and carried on past (the dispatcher does this for each failed job, since it exits 0 either way). The POST body, cut to its last 10,000 bytes, is the run's log. `HEALTHCHECKS_PING_URL` is set per cron service in the Render dashboard (it is a secret; the repo is public); blank, the default and always on staging, pings nothing. A ping that fails is a logged warning and never changes the run; Render runs a cron without a shell, which is why the ping lives in Python rather than in `cmd && curl`.

## Guidance (#1007: `core/guidance.py`, `core/whats_new.py`, `core/templatetags/guidance.py`)

`core/guidance.py` is the registry of feature keys (`Guidance`: title, where it lives, steps, clip, tour, help key; `docs/GUIDANCE.md`), import-light so the two CI scripts can read it without settings. `registered(key)` says whether a key is a feature or an area with one under it (`guild` covers `guild.*`, `covers`), and `title_for(key)` is the registered title, `AREA_TITLES` for an area ("Admin Tools", "Guilds", "Home", "Classes") or the key's last segment in Title Case. `core/whats_new.py` reads the composed changelog for one viewer: `whats_new_for(request)` is the one `WhatsNew` per request (the roles query runs once, however many things on the page ask), with the window's entries by tab and by feature, `is_unseen`, `has_unseen(feature)` (the badge and the button's pulse) and `has_entries(feature)` (any age: whether the feature's button renders at all), and `mark_seen` on `Member.whats_new_seen`. `core/templatetags/guidance.py` is `{% new_badge "<key>" %}` and `{% whats_new_button "<key>" %}` (`labelled=True` and no key for Home's); a key registered nowhere raises under `DEBUG` and logs in production, and `tests/hub/guidance_keys_spec.py` holds every key a template writes to the registry. Placements and the click script are `hub/AGENTS.md` and `FRONTEND.md`.
